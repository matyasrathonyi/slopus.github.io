# How It Works

Happy (2) is one server, one database, and clients that reconcile against it. There is no peer-to-peer state, no event log to replay, and nothing important stranded on someone's laptop.

## One server owns the truth

A small Fastify server owns authentication, persistence, files, collaboration state, realtime updates, and agent execution. You run it, so channels, messages, documents, files, agent state, grants, and secrets stay on infrastructure you control.

The server can run in three roles: `all` (authentication plus the product API), `auth` (authentication only, as a separately deployed identity service), or `api` (validation only, given the matching public key). The default is `all`, which is what `npx happy2` starts.

## Sync is reconciliation, not replay

Clients hold a sequence number and ask the server what changed. Realtime events over the stream are only a hint that something happened, a delivery notification and never durable state. The client then reconciles through the difference API.

This is the Telegram model rather than the event-log model, and the practical difference shows up in two places. Revoked state actually disappears, because the client re-derives from the server instead of replaying everything it was ever handed. And a client that has been offline for a week catches up with one difference call instead of a capped replay window.

Every retried mutation carries one idempotency key across all attempts, so a retry after a dropped connection cannot duplicate work.

## Agents run in sandboxes

Agent execution happens on the server through [Rig](https://github.com/slopus/rig), our shared runtime. Happy (2) manages its own private Rig daemon under `.happy2/rig` and never touches a Rig you installed globally.

Every chat gets a container, Docker or Podman, chosen once when you set the server up. The rootfs is read-only, `/tmp` and friends are tmpfs, and only the workspace and home directories are mounted in. Agent working directories live under `.happy2/workspaces`: a channel gets its own, and a direct message gets a per-person one, so one person's files never leak into someone else's conversation.

Sending a message to an agent does not open a long-lived request. The message and one work item per addressed agent commit **in a single transaction**, and a leased worker picks the item up. That is why an agent keeps working when you close the tab, why a teammate opening the same channel sees the same run, and why an interrupted turn resumes after the server restarts.

The honest tradeoff: some work you genuinely want local, on your own machine, your fastest hardware, your local toolchain. Server-side execution does not cover that case yet.

## Files

Files are served through short-lived signed URLs, and access is an explicit grant: a user, a chat, or the whole server, optionally expiring. You can set per-user and server-wide quotas, an expiry for incomplete uploads, and a quarantine retention window. An optional malware-scanner command runs before a file becomes available, and you choose whether a scan failure denies or allows the upload.

Alongside files, every chat exposes its agent's **workspace** as a browsable tree with an editor: live filesystem invalidation, background Git status, and saves that detect a conflicting write instead of clobbering it.

## Plugins

Plugins are containers that talk to a dedicated capability-only host API, a separate listener from the main server that defaults to port 3001. A plugin exposes MCP tools to agents and app surfaces to the UI, and receives permissions per install. See [Plugins](/happy2/docs/plugins/).

## Clients

Happy (2) is a **desktop** product. There is no mobile app and no mobile layout.

The web app is the full product: one React application, served by the same process that runs the server. In the all-in-one mode the API listens on an ephemeral loopback port and the SPA is served on the public one, with `/v0` proxied through internally, so the browser sees a single origin for HTTP, uploads, SSE, and WebSockets. Web sessions authenticate with an HttpOnly cookie, so no token is ever exposed to JavaScript.

There is also a macOS Electron app, which is a different and smaller thing: it is a client to a Rig runtime on your machine, or a window onto a Happy server you point it at. The complete workspace, meaning channels, documents, plugins, and administration, comes from a Happy server.

## The pieces

| Package | Responsibility |
| --- | --- |
| `happy2-server` | Authentication, persistence, files, collaboration, agent execution |
| `happy2-state` | Immutable client state and realtime reconciliation, framework-independent |
| `happy2-ui` | Reusable design system and cross-browser visual coverage |
| `happy2-app` | The shared React application for web and Electron |
| `happy2-web` | Browser entry point and production web build |
| `happy2-desktop` | macOS Electron app |
| `happy2-gym` | Isolated black-box server, state, and browser testing environment |
