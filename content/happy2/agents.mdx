# Agents & Permissions

Most agent products give you personas: named characters with keys, dragged from room to room. Open the app and three of them greet you. Multiply that by everyone on the team and you get a directory of AI goobers nobody asked for.

Happy (2) takes a different position, and it has two halves.

## An agent is a user

Creating an agent creates an ordinary user row with `kind = "agent"`: a real username, an avatar, a profile, a place in the member directory, and a normal two-person conversation with you. There is no agent-specific chat type and no bot-integration surface. Agents send messages through the same path humans do; they simply never accumulate unread badges.

That is what makes an agent addressable, mentionable in a member list, and a member of a channel rather than a feature of it.

## Its identity is the room

What the agent *is* at any moment is the channel it is working in: that channel's history, that channel's agent state, and that channel's sandbox. There is no portable persona carrying context between rooms.

One default agent is created when you set the server up. It is a member of every channel, the sender of service messages, and every person gets one permanent conversation with it. You are not assembling a cast before you can start.

Each chat can override the model and the thinking effort for its agent, and changing either leaves a visible service message in the timeline rather than silently altering behavior.

## How an agent is addressed

Not by typing a name in prose. A message is explicitly addressed to the agents in the chat, which reaches the channel's default agent plus any agents you name. Mention-driven invocation in prose is not how it works today.

## Every chat gets a container

Agents execute server-side through [Rig](https://github.com/slopus/rig) inside a Docker or Podman container. The rootfs is read-only, temporary directories are tmpfs, and only the home and workspace directories are mounted in. A child channel shares its parent's container while keeping its own history and settings.

Because the sandbox belongs to the chat rather than to a browser session, the work survives you closing the tab, and a teammate opening the same channel is looking at the same running thing. You can attach a real terminal to that container from the browser.

Agent work is durable, not in-flight: the message and the agent's work item commit in one transaction, a leased worker picks it up, and an interrupted turn resumes after a server restart.

## Permissions

There are two boundaries, and they do different jobs.

**The container is the blast radius.** Whatever the agent does, it does inside a sandbox with a read-only root and access to exactly one workspace.

**The grant is the tool surface.** The tools an agent can call are the ones resolved for it, meaning plugin tools from installations an administrator approved, with permissions declared in the plugin manifest and granted at install time. An agent does not discover its limits by attempting things and reading errors; the tools it was not given simply do not exist in its surface.

Server capabilities are separate again: concrete permissions such as `manageSecrets`, `managePlugins`, `viewAllMembers`, and `resetPasswords`, assignable directly or through custom roles.

We agree with the rest of the field on one prior point: an agent should never assume a human's credentials.

## Secrets are attached, not pasted

A secret is bound to an agent or a chat and forwarded to the runtime at execution time. It never becomes prompt text, and Happy (2) never persists the value. Only the assignment lives in Happy's database; the value is not stored and is never returned to a client.

## What is not solved

Some work belongs on your own machine: native builds, your fastest hardware, a device plugged into your desk. Happy (2) runs agents on the server, so that case is currently unaddressed. We would rather say so than pretend the tradeoff does not exist.
