# Plugins

A plugin in Happy (2) is a **container**, not a browser bundle and not code running inside the app. It talks to Happy through a capability-only host API and gets exactly the permissions granted when it was installed.

## What a plugin can offer

- **MCP tools for agents.** Tools from a ready installation are handed to the agent on every submission, so an agent in a channel can call them directly.
- **Skills.** Agent skills are reconciled into the sandbox before each turn.
- **Apps.** An HTML resource rendered in an iframe, either a navigable sidebar destination or a detached overlay.
- **Contributions.** Native controls at Happy-owned placements: the sidebar menu, the chat menu, the composer, the message menu, a settings section. Each one is bound to exactly one tool.

Extending the workspace does not mean forking it, and installing something does not mean handing it the server.

## The container boundary

Plugin containers are locked down harder than agent containers: all capabilities dropped, no new privileges, and explicit memory, CPU, and process limits. There is one container per *installation*, not per plugin, so two configured copies of the same plugin never share state.

## The host API

Plugin containers connect to a dedicated listener, separate from the product API:

```toml
[plugins]
directory = ".happy2/plugins"
host_api_host = "0.0.0.0"
host_api_port = 3001
```

It carries none of the `/v0` product routes. Every route is permission-gated, and the token a container authenticates with encodes its installation, its container incarnation, and the permissions it was granted. It binds to all interfaces by default so containers can reach it, so **firewall it from untrusted networks**.

Installing and managing plugins is administrator-only. You can install from the built-in catalog, a ZIP upload, an HTTPS link, or a GitHub repository.

## An agent can ask; a human approves

An agent's tool call gets a short-lived token bound to the session, the call, the human who triggered it, the agent, and the chat. That is enough for an agent to *stage* a plugin installation as a durable request in the timeline, which an administrator then approves. The agent cannot grant itself capabilities. The request is a message, not an action.

## Built in

The repository ships several plugins, which double as the reference implementations for the SDK:

| Plugin | What it does |
| --- | --- |
| Chat management | Create projects, channels, and child channels; update chat metadata; send messages |
| Documents | Read chat documents and propose block edits that wait for member approval |
| Environment management | List, create, reactivate, and set a default for the agent's own containers |
| Port sharing | Expose a container port at a public URL with a chosen audience |
| To-dos | Multi-instance lists with their own apps, sidebar instances, and storage |
| Plugin developer | Stage plugin installs and uninstalls for human approval |

`hello` and `movie-catalog` also ship, as minimal examples rather than things you would keep installed.

## Port sharing

Port sharing is itself a plugin, and it is the clearest demonstration of the model: an agent exposes a port from its sandbox at a public URL, to an audience you choose (the internet, everyone on the server, or just that chat) without anything else in the system learning about ports.

```toml
[port_sharing]
public_domain = "preview.example.com"
```

Omit the table to disable public agent-port sharing entirely. When enabled, configure wildcard DNS and TLS for `*.preview.example.com` pointing at the same Happy web listener.

Access is re-checked against durable state on **every** request, HTTP and WebSocket alike. Removing someone from the chat revokes their live preview immediately rather than at token expiry.

## Not yet

There is no marketplace, no in-place upgrade, and no OAuth for remote MCP endpoints. Update checks report that an installed snapshot has drifted from its source, deliberately without replacing it.
